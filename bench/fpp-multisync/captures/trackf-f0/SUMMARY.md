## Incident during capture: the Docker daemon died mid-session

`sleep`, computing elapsed time via `bc` every iteration) against the bench
container. Shortly after, the whole Docker daemon on the host stopped
responding (`docker ps` returned bare `EOF`) and then went down entirely —
confirmed by the orchestrator, who restarted Docker Desktop. That restart
killed every container on the host, including my own `showmesh-trackf-fpp`
(no restart policy) and briefly the shared `showmesh-bench-fpp-master` (which
came back on its own because it runs `restart: unless-stopped`). I did not
touch the shared container directly at any point; the daemon-level outage
affected it collaterally and it self-recovered.

Consequence for evidence quality:

- `04`-`33` (FSEQ duration proof, playlist read path, first start/idle
  capture) were taken on the pre-crash container and are exactly reproduced
  post-recovery (the `06`-`12` shapes match the redone playlist definitions
  after recreation) — not timing-sensitive, so unaffected either way.
- `34-cadence-poll.ndjson` (the first cadence/position poll, one-shot,
  non-repeat) was captured cleanly, before the busy-loop that preceded the
  crash, using the throttled `poll.sh` (real `sleep` between requests, no
  `bc` in the hot loop). It is not the run that caused the hang. I am still
  treating it as superseded rather than authoritative, per the
  orchestrator's instruction to re-take or label anything from that window
  as suspect: **`51`/`52` (graceful-stop timeline) and `60`/`71` (tight
  cadence poll and repeat-mode poll) are the captures the answers below
  actually cite for questions 3, 4 and 5.** Everything from `40` onward was
  taken after the container was recreated fresh post-recovery, on a host

- The busy-loop script itself (`35-tight-poll.ndjson`) produced zero bytes
  before the daemon died and has been deleted; nothing cites it.

`poll.sh` was fixed to accept `INTERVAL=0` (skip the `sleep` call, still no

built from ordinary `date`/`curl`, not the busy-wait that triggered the
outage.

## 1. FSEQ duration

**`pkg/fseq/fseq.go`'s exported surface is `FrameCount() int` and
`StepTimeMS() byte`. The controller's expression is:**

```go
durationMS := file.FrameCount() * int(file.StepTimeMS())
```

Proven in `01-fseq-duration.txt`, generated by the throwaway probe
`gen/main.go` (uses `pkg/fseq/fseqtest.Build` to synthesize valid FSEQ v2
files, then opens them with the real `pkg/fseq.Open`):

```
resting-300s.fseq:               FrameCount=6000 StepTimeMS=50 duration_ms=300000
dup-name/A/trackf-resting.fseq:  FrameCount=4800 StepTimeMS=25 duration_ms=120000
dup-name/B/trackf-resting.fseq:  FrameCount=1800 StepTimeMS=50 duration_ms=90000
zero-frames.fseq:                FrameCount=0    StepTimeMS=50 duration_ms=0
zero-steptime.fseq:              FrameCount=100  StepTimeMS=0  duration_ms=0
```

**Degenerate cases are the finding.** `FrameCount()==0` and `StepTimeMS()==0`
both silently multiply out to `duration_ms=0`, and are indistinguishable
from each other by the arithmetic alone. The controller must treat
`duration_ms == 0` as a stated failure (readiness rejects the resting FSEQ
as unusable, per RESTING-MODE §13's "parseable non-zero duration"), never as
"the boundary is now" — arming a deadline at `E == now` would immediately
fire every downstream transition cue. The check has to inspect
`FrameCount()` and `StepTimeMS()` individually, not just the product, so the
failure reason can distinguish "empty sequence" from "unset step time" for
the operator.

**No FSEQ v2 header field contradicts or supplements this.** Per
`docs/research/RES-017-fseq-format.md`'s byte table (offset 14: 4-byte frame
count, offset 18: 1-byte step time in ms), those two fields are the only
timing-relevant header contents; there is no separate duration/playtime
field. `StepTimeMS()`'s doc comment already warns against "correcting" the
byte to a true frame rate — this capture confirms raw multiplication is what
FPP itself does too (see question 6, where FPP's own `seconds_remaining`
matches this exact arithmetic).

## 2. Playlist definition read path

**Yes: `GET /api/playlist/:PlaylistName` returns the full ordered playlist
definition, including media association, independent of playback state.**
This is a config read (works while idle) — confirmed by creating the
playlist via `POST /api/playlist/:PlaylistName` and reading it back before
ever starting it (`06`, `07`, `08`).

One-item FSEQ-only resting playlist (`trackf-resting`), created and read
while idle:

```json
// 08-playlist-idle-read.json
{"name":"trackf-resting","mainPlaylist":[{"type":"sequence","enabled":1,"playOnce":0,"sequenceName":"trackf-resting.fseq"}],
 "leadIn":[],"leadOut":[],
 "playlistInfo":{"leadIn_items":0,"leadIn_duration":0,"mainPlaylist_items":1,"mainPlaylist_duration":0,"leadOut_items":0,"leadOut_duration":0,"total_items":1,"total_duration":0},
 "version":4}
```

A playlist with an audio item (`trackf-resting-with-audio`, `type: "both"`
carrying both `sequenceName` and `mediaName`), which §6.1 requires readiness
to reject, reads back the same way (`09`, `10`, `11`):

```json
// 11-playlist-with-audio-idle-read.json
{"name":"trackf-resting-with-audio","mainPlaylist":[{"type":"both","enabled":1,"playOnce":0,"sequenceName":"trackf-resting.fseq","mediaName":"trackf-fake.mp3"}], ...}
```

So a readiness check can distinguish the two shapes (`type: "sequence"` vs.
`type: "both"`/`"media"` present in `mainPlaylist`) entirely from this one
idle GET, with no need to start the playlist or observe running state —
satisfying "readiness may never claim playlist contents from running-state
observations."

**One caveat found, not asked for:** `playlistInfo.total_duration` and
`mainPlaylist_duration` are always `0` for a `sequence`-type item — FPP only
sums the `duration` field on entries that carry one explicitly (e.g. a
`pause` entry), and a bare FSEQ sequence item never gets one. FPP's own
playlist metadata is not a duration source for a resting FSEQ under any
circumstance — this independently reinforces question 1's answer: the
controller must open the FSEQ file itself.

No plugin/config-import path was needed or probed, because the native read
path answers the question directly.

## 3. Playback evidence

Fields read from `/api/fppd/status` (all in the shipped `fpp.*` collector's
input surface per `internal/coordinator/collector/fpp/signals.go`):
`status_name`, `current_playlist.{index,count,playlist,type}`,
`current_sequence`, `seconds_elapsed`, `seconds_played`, `seconds_remaining`,
`milliseconds_elapsed`, `repeat_mode`.

**Start.** `GET /api/playlist/:name/start` (or `/start/:repeat`) returns
immediately (`21-start-response.json`: `"Playlist Starting"`, sub-40ms). The
first poll after that already shows `status_name: "playing"`,
`current_playlist.index: 1`, `current_sequence` populated — start evidence
is fast and reliable.

**Item identity.** `current_sequence` (exact FSEQ filename) and
`current_playlist.playlist` (playlist name) are both present and correct
throughout playback; both are `""` while idle — present-but-empty, not
absent (see the null/absent/empty finding below).

**Position and remaining.** `seconds_elapsed`/`seconds_played` (identical
values, whole seconds, monotonically increasing) and `seconds_remaining`
(whole seconds, monotonically decreasing) are reliable but coarse.
`milliseconds_elapsed` is the only sub-second field and is present only
while `status_name` is a playing/stopping state — see question 4 for its
granularity.

**Pause.** Not exercised in this pass — see "Needs real hardware" below;
this is a bench-reachable gap the orchestrator's triage (7 and 3 before 5
and 6) deferred, not a hardware limitation.

**Item end / playlist end — completion evidence, not stop acceptance.**
This is the direct test of §7.2. Sequence: start `trackf-cadence` (20s,
one-shot), poll every ~0.2s, issue `GET /api/playlists/stopgracefully` ~2.8s
in, keep polling (`50-gracefulstop-timeline.txt`, `51`, `52`):

```
50-gracefulstop-timeline.txt:
  start dispatched      1787081614.372930000
  stopgracefully issued 1787081617.173684000
  response: "Stopping"  (received 1787081617.196022000 -- 22ms round trip)
```

```
51/52 poll trace (excerpt, t=0 is playlist start):
   2.796s status=stopping gracefully  s_el=2  s_rem=17  idx=1  playlist=trackf-cadence
   ... (status stays "stopping gracefully" for the rest of the ORIGINAL 20s duration) ...
  19.914s status=stopping gracefully  s_el=19 s_rem=0   idx=1  playlist=trackf-cadence
  20.092s status=idle                 s_el=None s_rem=0 idx=0  playlist=''
```

**`stopgracefully` returning `200 "Stopping"` at t=2.8s is not completion
evidence — the sole item ran to its full natural 20s end anyway**, because
"graceful" here means "let the current item finish," and this playlist has
only one item. The only observable completion evidence is the transition of
`status_name` from `"stopping gracefully"` (or `"playing"` for an
un-stopped end) to `"idle"`, together with `current_playlist` clearing.
There is no separate "item ended" or "playlist ended" event/flag; the
controller must diff consecutive polls for exactly that status/identity
transition.

**Absent vs. null vs. empty, confirmed live** (`90-idle-status-full.json`):
while idle, `milliseconds_elapsed` and `seconds_elapsed` are absent keys
(not present in the JSON at all); `seconds_played`/`seconds_remaining` are
present, reset to the string `"0"`; `current_sequence` and
`current_playlist.playlist` are present, empty string `""`. Three different
states on three different fields of the same response — a decoder that
defaults a missing key to `0` cannot be distinguished from one that read a
real `0`.

**One more type-inconsistency, confirmed, not new:** `repeat_mode` is a JSON
number (`1`) while playing with repeat armed, but a JSON string (`"0"`)
while idle. This matches why the shipped decoder
(`internal/coordinator/collector/fpp/decode.go`'s `numberField`/`intField`)
already parses through `strconv` rather than assuming a fixed JSON type —
this capture is a second independent confirmation of that defensive
decoding choice, not a new defect.

## 4. Cue cadence

Fast poll of `trackf-cadence` (20s FSEQ, `stepTimeMS=50`) with no `sleep`
between requests (`60-tight-cadence-poll.ndjson`, 384 samples over 7.7s,
measured via `curl`+`date`, not the busy-loop that preceded the crash):

- **Achieved poll rate:** mean gap 20.2ms, median 19.8ms, max 38.3ms — about
  49 req/s sustained against this bench container.
- **Single-request latency** (`61-request-latency.txt`): 1.8-16.2ms on
  loopback, mostly under 5ms after the first request.
- **`milliseconds_elapsed` does not advance continuously.** It changes in
  discrete jumps of exactly 50ms — matching this FSEQ's `stepTimeMS`
  exactly — and holds constant between ticks (154 changes recorded, every
  single one a jump of exactly 50, none larger or smaller). Position
  evidence is quantized to the FSEQ's own frame step time, not a
  continuously interpolated wall-clock value. `seconds_elapsed` is
  quantized to whole seconds, coarser still.

**What this means for cue-cadence design:** a single accurate
`(observed position, wall-clock time of that observation)` pair is enough to
compute the expected boundary to within one frame-tick (50ms here, and never
worse than the deployed resting FSEQ's own step time) — comfortably inside
the ±250ms tolerance from one sample. The armed deadline should be a local
monotonic timer derived once, corrected only by later observations that
contradict it (restart, seek, pause, item mismatch — per RESTING-MODE §6.2),
not re-derived every poll. **The ordinary 15-second collector cadence is
unusable as the correction source near the boundary**: a single missed
alignment at that cadence can leave the controller up to 15s stale, two
orders of magnitude past tolerance. The correction/backstop poll needs to
run at a materially faster cadence (sub-second, e.g. every 250ms-1s) only in
the window approaching the expected boundary; away from the boundary the 15s
collector cadence is fine for gross-drift detection (restart/seek/wrong-item),
since those are large, unambiguous discrepancies, not ±250ms-precision
events.

## 5. Repeat and one-shot

**Requested via the start command itself**, not a separate config write:
`GET /api/playlist/:name/start/:repeat` where `:repeat` is `true`/`false`
(`21`, `33` used `/start/false`; `70` used `/start/true`). This matches the
already-shipped `startPlaylist` primitive's `repeat` argument
(`docs/bench/fpp-command-vocabulary.md` line 306).

**Observed via `repeat_mode`** (`0`/`"0"` vs. `1`) plus the position fields
wrapping. One-shot (`51`/`52`, `/start/false`): item plays to its natural
end and `status_name` transitions to `idle` — no automatic restart, per
question 3's completion-evidence trace.

Repeat (`70`, `71-repeat-poll.ndjson`, `/start/true`, 45s poll against the
20s item): `status_name` stays `"playing"` continuously across loop
boundaries — confirmed wraps at t≈20.4s and t≈40.4s where `seconds_elapsed`
drops from 19 back to 0 with `current_playlist.index` unchanged at `1` and
`repeat_mode` staying `1` throughout. There is no idle gap and no distinct
"loop" event — the only signal that a new cycle started is
`seconds_elapsed`/`milliseconds_elapsed` decreasing instead of increasing
between two consecutive polls. `resting-intershow` (one-shot) and
`end-of-night-resting` (repeat) both use exactly this same start command and
the same position-field vocabulary; the controller distinguishes them by
which `:repeat` value it requested and by watching for a decrease
(repeating) vs. a transition to idle (one-shot) as the loop/end signal.

## 6. Same-filename target variants

Two FSEQ files generated with the same original filename
(`trackf-resting.fseq`, as xLights would emit per target) but different
content — `dup-name/A` (4800 frames × 25ms = 120000ms) and `dup-name/B`
(1800 frames × 50ms = 90000ms), content hashes `39c4b17d5d52feee...` /
`e6193fefc2d78c91...` — were uploaded to FPP's flat sequences directory
under distinct target-qualified names (`trackf-resting-variantA.fseq`,
`trackf-resting-variantB.fseq`, since FPP's own filesystem cannot hold two
files with one name), wrapped in their own one-item playlists
(`trackf-variantA`, `trackf-variantB`), started, and observed:

```
A: seq= trackf-resting-variantA.fseq  seconds_remaining= 119   (expected 120000ms)
B: seq= trackf-resting-variantB.fseq  seconds_remaining= 89    (expected 90000ms)
```

Both match the independently-computed `FrameCount()*StepTimeMS()` duration
for their respective files (within FPP's own 1-count-down floor behavior).
**This demonstrates concretely why filename alone cannot be the resting-FSEQ
identity** (ADR-028): FPP's own directory is flat and cannot even hold two
identically-named per-target renders simultaneously, let alone disambiguate
them at read time. The controller must carry the full ADR-028 identity —
show + sequence + target + content hash — and resolve "the deployed resting
FSEQ for this FPP target" to the specific uploaded filename FPP is actually
running, verifying its content hash against the pinned Night Session
revision rather than trusting a shared logical name.

## 7. Brightness

**Destructive-only. There is no path to observe a currently-scheduled
ceiling separately from the full stored configuration, and no partial-write
path — a caller can only overwrite the entire processor list.**

- **No brightness command exists in FPP's command vocabulary at all.**
  Checked directly against the FPP source (`grep` over
  `/opt/fpp/src/commands/Commands.cpp`'s 40 registered commands): none of
  them mention brightness, dimming, or gamma. `docs/bench/fpp-command-vocabulary.md`
  (Step 8's capture) independently confirms the same absence.
- The only brightness-shaped control is a static per-channel-range output
  processor, `GET`/`POST /api/channel/output/processors` (`40`-`43`), whose
  entries are `{type: "Brightness", active, description, start, count,
  brightness (0-100), gamma}`. FPP's own `endpoints.json` marks this
  endpoint `"fppd": false` — it is served entirely by the PHP web layer
  reading/writing a JSON config file
  (`channel_get_output_processors`/`channel_save_output_processors` in
  `/opt/fpp/www/api/controllers/channel.php`), and confirmed by direct
  source read that the `POST` handler does no partial update: it
  `file_put_contents`s the entire request body over the whole config file,
  unlike the DMX-config sibling function a few lines above it in the same
  file, which explicitly calls `SendCommand('w')` to notify the running
  `fppd` — the brightness save path has no equivalent notification call.
- **It does apply live without a restart**, confirmed structurally (not by
  a visual light test — this bench container has no attached fixture):
  `ChannelOutputSetup.cpp` registers a `FileMonitor::INSTANCE.AddFile(...)`
  watch on `outputprocessors.json` that calls
  `outputProcessors.loadFromJSON(newRoot)` and `ComputeOutputRanges()` on
  every change, and `outputProcessors.ProcessData(channelData)` runs once
  per output frame. So a write does take effect on the running show without
  a restart — but it is still a full-array overwrite of the stored
  configuration, not an incremental adjustment, and `/api/fppd/status`
  carries no brightness field at all, so there is no independent "current
  effective ceiling" to read back that is distinct from "whatever this same
  config file currently contains."
- Round-trip proof (`41`, `42`, `43`): `POST` with one entry
  (`brightness: 60`) is echoed back verbatim by the following `GET` — the
  response IS the stored config, with no derived/observed field alongside
  it.

**One unambiguous sentence for the owner:** FPP exposes brightness only as a
full-array destructive overwrite of a static per-channel-range config file
with no companion "currently scheduled ceiling" observable and no
partial-update path, so a ShowMesh transition-gain provider cannot compose
an independent multiplier against FPP's own schedule without racing
whatever last wrote that same file — the compositional model RESTING-MODE
§7.3 describes (`effective = FPP ceiling * ShowMesh transition gain`) is not
supported by anything FPP exposes today. Per §7.3 and this seam's own
instructions, this is an owner decision: either accept the
destructive-overwrite limitation and design around it explicitly (e.g. only
ever letting one side own the array, reserving disjoint channel ranges per
side, or moving board-level dimming into ShowMesh's own render path instead
of FPP's output processors), or select a different lighting
provider/authored-FSEQ-fade path for the transition brightness composition
F4 needs.

## Needs real hardware

- **Pause/restart evidence (question 3)** was not exercised in this pass —
  triage under the orchestrator's priority (7 and 3 before 5 and 6) covered
  start/position/remaining/item-end/playlist-end/repeat but not an explicit
  pause-then-resume cycle. This is bench-reachable, not a real-hardware gap,
  and should be picked up in a follow-on F0 pass or folded into F2/F3's own
  testing before that behavior is claimed.
- **Real per-installation timing** (network latency to a physically
  deployed FPP host instead of loopback, GPIO/relay-driven brightness
  hardware if any deployment uses it instead of FPP's software output
  processors, and multi-hour drift behavior of `milliseconds_elapsed`'s
  50ms-quantized ticks over an actual multi-minute resting FSEQ) needs the
  reference installation and is out of reach of this bench container by the
  seam's own rule.
- **Whether any deployed FPP host has a working `fpp-brightness` plugin or
  other brightness-adjacent plugin installed** was not checked — this bench
  image has no plugins installed, and the plugin ecosystem is a punch-list
  item, not something this capture can rule in or out.
