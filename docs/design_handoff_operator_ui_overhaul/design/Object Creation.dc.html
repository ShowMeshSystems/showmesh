Pattern · D-011 and D-017

Creating and editing config objects

Ruling on both entries is B, so the forms are drawn here. Five instances of one pattern: new show, new playlist, new action, editing an action, new macro. Nothing new in the kit — every control is one the shipped mocks already use.

The rule

Creation is the object's own edit surface, opened empty. There is no create-modal in this UI. Whatever surface edits the object — a full-width form on Shows, the right-hand aside on Automation — is the surface that creates it.

  1. The id is the only field creation has that editing does not. It seeds from the name, stays editable until the first save, and is locked with the object's own immutability copy afterwards. A modal that collects an immutable id and then hands off teaches the operator the id was a throwaway.
  2. One gate field first when the rest of the form depends on it. A playlist's runner and an action's integration each decide which fields are even legal. The gate is a segmented control, and nothing below it renders until it is answered — not disabled, absent.
  3. Draft is stated, not implied. The pane header reads Draft where an existing object reads Editing, and the footer says what the save writes: Creates for a draft, Creates revision n for an edit.
  4. Nothing is written before the save. No optimistic row in the table behind it. A refused PUT leaves the draft open with the coordinator's reason above the footer, in the pattern Live Control already uses for refusals.
  5. Never defaulted stays never defaulted. An action's safetyClass and a step's localFallback.reason have no schema default, so the draft opens with them unanswered and the save is withheld until they are — the one legitimate disabled save in the pattern.

5 · New macro

Shows › Automation, right aside · PUT /config/show.macro/{id}

No gate — a macro's shape does not vary. It asks for a label, an id and a first step, then hands straight to the drawn step editor. A macro with no steps is refused, so step 1 is part of creation rather than something to add afterwards.

Reuse

Settings and Access create objects too, and they get the same pattern rather than a variant: their own detail surface opened empty, id unlocked, one gate where the shape varies (an audio node's transport, a role's scope). Nothing here is Automation-specific.

A refused save keeps the draft open and renders the coordinator's reason above the footer — the same treatment Live Control uses when a lifecycle command is refused. There is no toast.

Cue creation is already drawn: the Show Cues two-pane composer predates this and stays as it is. It is the same rule — the composer is the cue's edit surface.
