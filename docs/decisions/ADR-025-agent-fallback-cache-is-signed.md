# ADR-025: The Agent's Fallback Cache Is Signed, and Its Verifying Key Is Pinned at Enrollment

Status: Accepted
Date: 2026-08-12

## Context

[ADR-009](ADR-009-sqlite-configuration-storage.md) requires node agents to cache a "verified JSON subset (current assignment + fallback definitions) on local disk, **checksummed**, sufficient to execute reduced local fallback with the coordinator unreachable." [ARCHITECTURE §9](../architecture/ARCHITECTURE.md#9-configuration-model) requires agents to retain "the **signed or verified** subset."

Both sentences use the word *verified*, which is why the disagreement survived this long. ADR-009 then specifies a checksum; ARCHITECTURE admits a signature. Those are different security properties, and [RES-008](../research/RES-008-configuration-model.md) §3.3 recorded the contradiction. The owner chose signing.

Choosing signing is the easy half. Signing introduces a trust anchor, and the trust anchor collides with a constraint this project has already recorded.

### The collision, stated before it is resolved

[ADR-024](ADR-024-identity-authorization-and-audit.md)'s consequences record that delivering broker credentials from the coordinator "would give a rebooting node a boot-time coordinator dependency it does not have today, which ARCHITECTURE §11's power-restoration case would find." A verifying key has exactly that shape, and the collision is worse than it is for a credential.

**The cache exists for the case where the coordinator is unreachable.** If a node must reach the coordinator to obtain the key that lets it verify the cache, then a node rebooting during a coordinator outage cannot use its cache. The mechanism would fail precisely and only in the situation it was built for, and it would do so silently, because from the node's point of view an unverifiable cache and a missing coordinator look the same.

### The finding that determines the answer

**The security value of a signature lives entirely in where the verifying key sits**, and the three cases are not close:

- **Checksum.** An attacker who can write the cache recomputes the checksum. Zero origin guarantee. This is ADR-009 as written.
- **Signature, verifying key in a file the same attacker can also write.** They replace both. Also zero origin guarantee, while presenting as signing in the code, in the logs, and in any document describing it.
- **Signature, verifying key not writable without privileges that already permit replacing the agent binary.** Real, because subverting the anchor now costs the same as subverting the thing the anchor protects, which is the honest ceiling for on-host integrity.

The middle case is the one to worry about, because it is the easiest to build, it looks correct from every angle except the one that matters, and nothing in a test suite distinguishes it from the third. This record exists as much to forbid the middle case as to choose signing at all.

### What this actually defends against, stated honestly

On an isolated show LAN running the operator's own hardware, the realistic threat is not a targeted intruder, and a record that oversells the adversarial case invites a later contributor to cut it as paranoia.

The failures this catches are operational: **a cloned SD card, a node restored from the wrong backup, a cache left behind from a different installation, a node returning after months in a box.** Every one of those produces a cache that is internally consistent, passes a checksum, and is wrong. A per-deployment signature catches all of them, because a cache from another installation does not verify against this installation's key. That is the primary value. The intruder case is real but secondary.

## Decision

**1. The cache is signed, not checksummed.** This supersedes ADR-009's `checksummed` clause and narrows ARCHITECTURE §9's "signed or verified" to signed. Ed25519, which is in Go's standard library and needs no CGo, satisfying [ADR-012](ADR-012-docker-coordinator-deployment.md).

**2. The keypair is per deployment, generated by the coordinator at first run.** Same posture as ADR-024 decision 10's broker credentials: never authored into this repository, never shipped in the deploy bundle, because a key shipped in the bundle is identical in every installation and therefore establishes nothing. The private key never leaves the coordinator's data volume and is excluded from export bundles, including the [RES-008](../research/RES-008-configuration-model.md) D4 opt-in that permits exporting other secrets.

**3. The verifying key is delivered once, at enrollment, and pinned on the node.** Enrollment is an operator-initiated action, so the coordinator is reachable by definition at that moment. From then on the node verifies entirely offline. **No boot path, startup sequence, or fallback path may contact the coordinator to obtain, refresh, or revalidate a key.** This is the clause that discharges ADR-024's recorded constraint, and it is the reason the mechanism survives the outage it exists for.

**4. The pinned key must not be writable by anything that compromising the agent alone would grant.** It is owned by root and readable, never writable, by the account the agent runs as. **A verifying key stored where the agent itself could rewrite it provides checksum-level protection while presenting as signing**, which is the failure this decision exists to prevent. An implementation that cannot meet the ownership requirement on its platform must report that it is unverified rather than verify against a key it could have written itself.

**5. A node holds a key set, not a single key.** Rotation is add-then-retire, never a flag day. **Adding or removing a key is an operator action and is never an automatic coordinator push**, for two reasons that point the same way: an automatic push is exactly the channel a compromised coordinator would use to install its own anchor, and it would reintroduce the boot-time dependency decision 3 removes.

**6. Verification failure discards the cache, reports the condition, and does nothing else.** An agent whose cache fails verification behaves exactly as an agent with no cache: it has no reduced local fallback and says so. It must **not** execute the unverified content, and it must **not** refuse to start, refuse to connect, or otherwise escalate, because that would turn signing into a new way to stop a show. The condition is evidence carrying a state and a reason per [ADR-011](ADR-011-context-aware-observability.md) and [ADR-020](ADR-020-control-api-shape-and-change-stream.md), not a log line. This is the same shape as stale evidence reading `unknown`: the honest answer to "can this node run its fallback" is no, and the operator is told why.

**7. Enrollment while the coordinator is unreachable is a defined state, not an error.** Such a node has no pinned key, therefore no usable cache, therefore no reduced local fallback. That is legitimate and degraded, it must be visible as such, and it must resolve on the next successful enrollment. It must not block the agent from starting, advertising, connecting later, or doing anything else it can do without a cache.

## Consequences

- **Rotation touches every node**, which is the price of decision 3 and is mitigated rather than removed by the key set in decision 5. This is acceptable because a verifying key is not a credential that leaks through normal use, so rotation is rare, and because the alternative is a boot-time coordinator dependency that fails during an outage.
- **Restoring a coordinator backup restores the signing key, so existing node caches stay valid.** That is deliberate. It looks like it contradicts ADR-024 decision 5, whose session generation counter also rolls back with the database and which that record had to correct as a defect, and it does not. The rule that makes both correct is worth stating, because a third piece of state will raise the same question and "these two disagree, do not touch them" answers nothing:

  **A restore must preserve identity and must not resurrect revocations.**

  A signing key is an **identity**: it asserts that this installation is this installation, so restoring it restores a true fact, and caches signed under it really do belong to this coordinator. A generation counter is a **revocation record** whose only job is to be monotonic, so rolling it back silently un-revokes sessions an operator deliberately killed. Same mechanism, opposite verdicts, for a reason rather than by coincidence. Invalidating every node's cache on restore would also strip local fallback from the whole fleet at the moment an operator is recovering from something, which points the wrong way for the same reasons decision 11 of ADR-024 carves out blackout.

- **Applying that rule to this record exposes one thing it would otherwise have missed: key *retirement* is a revocation.** Decision 5's key set means the coordinator tracks which of its keys are current and which are retired, and that state lives in the coordinator's database. **A restore rolls it back**, so a coordinator restored from a backup taken before a rotation resumes signing with a key the operator retired, and any node still holding that key in its set accepts the result. This is precisely the shape ADR-024 found in its own decision 5, and it inherits that record's conclusion rather than needing a new mechanism: **a database cannot detect its own restore**, so the guarantee cannot be automatic and must be an explicit operator step. The restore runbook must therefore verify the current signing key alongside ADR-024's existing `invalidate-all-sessions` step, and a rotation is not complete until the retired key is out of every node's key set, which is decision 5's operator action rather than a coordinator push.
- **Re-provisioning a coordinator from scratch generates a new key and invalidates every node's cache.** Correct, because those caches came from a different installation, and it is the operational case in the context section.
- **The agent gains signature verification and a pinned key file to manage**, and enrollment gains a step. [RES-015](../research/RES-015-fpp-plugin-distribution-model.md) already establishes that the FPP-side installer runs as root, so writing a root-owned key file at enrollment is available on that path.
- **Nothing here is verified.** No cache exists, no enrollment flow exists, and [RES-009](../research/RES-009-failure-mode-testing.md) gains rows for verification failure, enrollment during an outage, key rotation mid-show, a node returning with a cache signed by a retired key, and a coordinator restored from a backup predating a key rotation.

## Alternatives considered

**Checksum only, ADR-009 as written.** Rejected. It gives no origin guarantee, and the failures that actually happen here, a cloned card and a wrong restore, are origin questions. A checksum answers "is this file intact", and the question is "is this file *ours*".

**The coordinator delivers the verifying key at each agent start.** Rejected as the central error this record exists to avoid. It reintroduces the boot-time coordinator dependency ADR-024 recorded, and it fails in exactly the scenario the cache exists for.

**Bake the verifying key into the agent binary at build time.** Rejected on a fact rather than a preference: the agent is a generic release artifact fetched by the FPP plugin per RES-015, and the keypair is per deployment, so the key cannot be known when the binary is built. It would also make rotation a rebuild and redeploy of every node.

**Give each node its own signing key so nodes can sign for one another.** Rejected. There is no use case, and it would place private keys on the least protected hosts in the installation, which RES-015 §7.4 shows cannot keep a secret.

**Use TLS or mTLS on the cache transport instead of signing the artifact.** Rejected because it solves a different problem. Transport security protects the delivery; the threat here is a cache already sitting on disk, which no transport can speak to. ShowMesh also terminates no TLS per [ADR-022](ADR-022-operator-ui-serves-the-api-same-origin.md).

## Supersession

Supersedes the word `checksummed` in [ADR-009](ADR-009-sqlite-configuration-storage.md)'s third decision paragraph. Everything else in ADR-009 stands, including that the agent caches a subset at all, that it must be sufficient for reduced local fallback, and that a stale returning node must not overwrite coordinator state. Narrows ARCHITECTURE §9's "signed or verified" to signed.

This record decides the trust model and the key's lifecycle. It deliberately does **not** decide what the cache contains, how it is distributed, or when it is refreshed. Those are RES-008 and macro-step questions, and no ADR-008 topic carries configuration today.
